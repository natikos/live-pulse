# Event contract

**Status: agreed** (issue #1). This is the contract client teams integrate against; the server must behave exactly as described here. Any change to it is a contract change and needs a new decision in `docs/DECISIONS.md`.

## Envelope (common to all events)

| Field | Type | Required | Notes |
|---|---|---|---|
| `event_id` | UUID string | yes | Generated by the **client, once per event**, and reused in every retry of that same event. The server deduplicates by it (see Duplicates). An invalid UUID is rejected. |
| `type` | `"page_view"` \| `"purchase"` \| `"error"` | yes | Unknown type is **rejected** with a message naming the field. |
| `source` | `"web"` \| `"mobile"` \| `"server"` | yes | Which client sent the event. Used to split metrics by platform. |
| `occurred_at` | integer, Unix time in **milliseconds** (UTC, e.g. `1792262054802`) | yes | When it happened on the client. Seconds are not accepted: a value in seconds is far too small and is rejected by the range check. Strings (including ISO dates) are rejected. A value more than 5 minutes ahead of the server clock is rejected (5 minutes covers ordinary clock drift between the device and the server; the value is configuration, not hard-coded). Past values are accepted (clients may buffer events offline), but not older than 30 days (configuration, `MAX_EVENT_AGE_MS`); older events are rejected naming `occurred_at`. |
| `user_id` | string | no | Known (logged-in) user. |
| `device_id` | string | yes for `web` and `mobile` | Device/visitor id. Always sent by clients, for every event type. |
| `payload` | object | yes | Shape depends on `type`. |

The server also stores `created_at` (when we received the event). Clients do not send it.

Identification rules:
- Clients (`web`, `mobile`) always send `device_id`, for every event type; `user_id` is added when the person is logged in. This lets errors be matched with what the same device did (for a possible future analysis of why people do not pay).
- Events with `source = "server"` have neither field required; `user_id` is added when the event concerns a specific person (e.g. a failed confirmation email).
- Unique people are counted by `user_id` when present, otherwise by `device_id`. Known limitation: a person who was anonymous and then logs in is counted twice.
- `user_id` is the sender's identifier of a person and must stay the same for that person over time, including guest customers (the backend creates a guest record at purchase) who later register. We do not distinguish guest from registered ids and do not merge them: if a sender changes the `user_id` of the same person, that person is counted twice.

Length limits: every id-like string (`user_id`, `device_id`, `page_id`, `entity_id`, `order_id`, `items[].id`) is at most 128 characters. A longer value is **rejected** naming the field, never truncated. Limits per field are in the tables below.

Keys are `snake_case` only. Other spellings (`pageId`) are rejected, not normalised.

## `page_view`

| Field | Type | Required | Notes |
|---|---|---|---|
| `page_id` | `home` \| `catalog` \| `category` \| `item` \| `cart` \| `checkout` \| `my-orders` | yes | Agreed vocabulary, the same for web and mobile. A value outside the vocabulary is still **accepted and stored** (a new page may ship before this list is updated); events with unknown pages can be found by querying for them. |
| `entity_id` | string, max 128 characters | required for `category` and `item` | Category id / item id. Not sent for the other pages. |
| `referrer` | string, max 2048 characters | no | Where the visitor came from. |
| `utm_source` | string, max 128 characters | no | e.g. `newsletter`. |
| `utm_medium` | string, max 128 characters | no | e.g. `email`. |
| `utm_campaign` | string, max 128 characters | no | e.g. `autumn_sale`. |

`cart` and `checkout` mean "the visitor saw this screen", not "did an action". Skipping `cart` (add-last-item-and-go-to-checkout) is legal; funnels are counted by unique people per step, not by sequence.

## `purchase`

Identification: the backend sends the `device_id` of the device the customer used when the order was placed, whenever it has one (and `user_id` for logged-in customers). It is optional: a purchase without it is still accepted, because revenue is never dropped, but it cannot be linked to the checkout step for guests. Known limitation: if the customer checks out on one device and pays on another, the ids differ and a guest purchase is counted as unlinked. Purchases that carry neither `user_id` nor `device_id` can be found by querying the stored data.

**Only the backend sends `purchase`** (`source = "server"`), after the payment provider has confirmed the payment. A `purchase` with `source` `web` or `mobile` is **rejected** with a message naming the `source` field. Reason: revenue and order counts must match finance and the payment provider exactly, and an app can claim a purchase that later fails, or be closed before it reports one.

| Field | Type | Required | Notes |
|---|---|---|---|
| `order_id` | string, max 128 characters | yes | Business order id. Stored as data; **not** used for deduplication (that is `event_id`). |
| `channel` | `"app"` \| `"phone"` \| `"admin"` | yes | Where the order was placed. Closed list: an unknown value is **rejected**, so a new channel must be added to this contract and deployed on our side **before** the backend starts sending it. Only `app` orders belong in the app funnel conversion; revenue and order counts include every channel. |
| `sum` | integer, minor units (kopiyky) | yes | What the customer actually paid (delivery and discounts included). Greater than 0. |
| `items` | array, 1 to 100 positions | yes | Purchased positions. |
| `items[].id` | string, max 128 characters | yes | Item id, the same id as `entity_id` of the item page. |
| `items[].unit_price` | integer, minor units | yes | Price of one unit actually paid by the customer (after discounts). Position total is `unit_price * quantity`. |
| `items[].quantity` | integer, 1 to 100000 | yes | The business reports wholesale orders of up to ~50000 units of a cheap item. |

`sum` and `unit_price` have no business upper limit: revenue is never rejected for being large. Only the technical range applies (a safe integer, so sums stay exact). Orders that look suspicious (e.g. `sum` above 10 million UAH) are meant to be flagged for review at read time, not rejected; that is a later dashboard ticket.

`sum` is **not** required to equal the sum of the positions (delivery, promo codes). A mismatch alone never rejects the purchase.
Currency: there is a single currency, UAH. All amounts (`sum`, `unit_price`) are integers in kopiyky (1/100 UAH), and there is no currency field. Selling in another currency would be a contract change.

Duplicates (all event types): the first event for an `event_id` wins. A repeated event is not stored again and the client still gets a success response (`201` for a new event, `200` for a duplicate). Uniqueness is enforced by the database, not by application code.
Reusing an `event_id` with a **different body** is a client error. The server does not compare bodies: the first event wins and the later one is dropped silently (the client still gets `200`).
Known limitation: two events for the same `order_id` with **different** `event_id`s are both stored. Senders must reuse the `event_id` when retrying. Double reporting of a purchase from two sides is prevented by the rule that only the backend sends `purchase`.

## `error`

Errors are for analytics (counting, grouping, correlating with users who did not reach payment). Critical errors and stack traces are handled by a dedicated error tracker, not by this service.

| Field | Type | Required | Notes |
|---|---|---|---|
| `operation` | open vocabulary (e.g. `add_to_cart`), any non-empty string up to 64 characters | yes | What was being done. Business-level name, stable across routes and platforms. Also covers background work with no user action (cron jobs). |
| `code` | open vocabulary (e.g. `network`), any non-empty string up to 64 characters | yes | Short, stable error category used for grouping. |
| `page_id` | open, same as `page_view` (unknown values accepted and stored) | no | Where the user was. Only sent when known (clients). Not sent for background work. |

`operation`, `code` and `page_id` are open on purpose: a new page, operation or error kind must not cause an error event to be rejected and lost. Known values are listed in the TypeScript model for autocomplete only, and unknown values are found by querying the stored data. Decided by the client; the values are not validated against a list.

No free-text message: it is useless for grouping, may contain personal data, and needs a size limit. Stack traces are not accepted. Adding an optional message later is a safe extension.

The platform comes from the envelope `source`, so it is not repeated in the payload.

## Responses

- Accepted: success status (see duplicates above).
- Rejected: `400` with `message`, a list of strings, one per problem, in the form `field: reason` (for example `device_id: device_id is required for web and mobile events`). An unknown key is reported as `Unrecognized key: "name"`. Nothing is stored.
